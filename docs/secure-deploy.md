# Secure Cloudflare Worker deployment

## Scope and availability

`secure_worker_deploy` is an owner-authorized, per-Computer private deploy operation, not a general shell tool. v1 supports only an already-bundled JavaScript Worker module selected by an owner-pinned relative workspace path and SHA-256 digest. It does not run repository build scripts, Wrangler config, plugins, hooks, arbitrary commands, non-JavaScript Worker assets, Timber infrastructure deployments or a production release pipeline. The trusted Computer controller snapshots the bounded regular artifact, verifies the pinned digest, and dispatches that exact immutable byte sequence to a dedicated unprivileged deploy UID. A separate fixed, pinned Wrangler executable receives only its Cloudflare credentials over the private runner channel. Shell, PTY, browser and build processes remain a different unprivileged UID with no sudo/setuid/capabilities and cannot inspect the deploy UID's process environment. Credentials are not put in generic exec, argv, workspace/R2, journal, tool output, events or logs.

The private route is `POST /secure-deploy` on the bot's existing ComputerDO/container control channel; it is not exposed as `ComputerAction` or host `exec`. Request data contains only the operation ID, signed metadata-only owner authorization, immutable pin, reference revision/permission bindings and ephemeral credential values. The trusted API checks plan revision/active state, bot/run/operation/Stop/deletion liveness, current credential ciphertext/revision and signed grants before dispatch. After any container start/restore await, ComputerDO calls the private WorkspaceDO `/keychain/deploy-verify` route with the signed envelope; WorkspaceDO verifies the HMAC, current plan and references, and checks the original run/native operation/Stop fence. The route is blocked at the public gateway. ComputerDO then checks local deletion/abort/expiry synchronously and invokes the token-authenticated private container route with no intervening await. The Computer route also enforces the private per-Computer bearer management token, exact pin/reference correspondence, safe artifact-path/open rules, digest and auth-format allowlists. Only a fixed `{operationId,status,code}` receipt is returned. Untrusted CLI output is suppressed. An uncertain dispatch is recorded as uncertain and never resent automatically.

A readiness probe performs no credentialed request: authenticated `GET /secure-deploy/capabilities` runs a synthetic cross-UID `/proc` canary and reports the real Computer image/runner checks. The owner-only API `GET /v1/keychain/deploy-capabilities?botId=<id>` forwards only that fixed capability schema. The named-bot host tool `secure_worker_deploy_capabilities` also checks that bot’s actual Computer (including startup/restore and canary), returns metadata only, accepts `{}`, and does not resolve or require keychain references. It is fenced by run/Stop/ownership checks and unavailable to temporary agents. Public `GET /health/version` exposes the deployed Worker version ID plus schema-derived private tool inputs; it contains no user or keychain data.

## Owner plan API

The existing authenticated owner API is used; no separate Worker or credential setup is introduced:

- `POST /v1/keychain/deploy-plans` accepts `{operationId,botId,repository,commit,artifactDigest,artifactPath,accountId,workerName,refs:[{id,revision}]}` and returns `{plan}`. Repeating the same operation ID and normalized details returns the original plan; different details conflict. The references must be permitted to the selected bot at the selected revisions and configured for Cloudflare API authentication.
- `GET /v1/keychain/deploy-plans` lists active owner plans. Bot-context aliases cannot list, create or revoke plans.
- `DELETE /v1/keychain/deploy-plans/:planId` accepts `{operationId,expectedRevision}`, revokes the plan and advances the revision. A stale revision is rejected.
- The model tool accepts only `{planId,expectedRevision}` and cannot retarget or select credentials. Owners can create plans through the authenticated API without placing credential values in the request.

The repository is `owner/name` with no dot path component; commit is exact lowercase 40/64-hex; digest is `sha256:` plus 64 lowercase hex; artifact path is a bounded relative path with no dot/traversal components; account ID is 32 lowercase hex; Worker name is bounded lowercase DNS-style text. Destination is constructed internally as `https://api.cloudflare.com/client/v4/accounts/{accountId}/workers/scripts/{workerName}`. Use one `Authorization: Bearer ` reference or both `X-Auth-Key` and `X-Auth-Email` references with empty prefixes. Extra fields, arbitrary URLs/commands/args/config paths and malformed references reject.

The WorkerDO resolves the owner plan, verifies bot binding and run state, and signs metadata only: owner/bot/run/operation, plan revision, target, artifact path/digest, reference revision, signed permission epoch and ciphertext/grant binding. The authorization is short-lived and never contains credential values. The owner keychain decrypts each reference only in a scoped callback immediately before the private Computer call; the callback drops its temporary references after request completion. The deploy UID receives only the exact allowlisted Cloudflare auth environment variables and the verified JS artifact through a private channel; ordinary workspace commands cannot inspect it. Journal fingerprints are keyed; deployment records contain only immutable public pins, status and allowlisted error codes.

## Security and recovery

Plan, ref, permission epoch, run/native operation, task Stop and bot deletion checks are repeated after awaits and immediately before the dedicated private route. Local admission is single-flight per bot and globally bounded; durable atomic operation reservation prevents duplicate dispatch across coordinator instances. The final DO request is the only dispatch. A saved in-progress receipt after eviction becomes uncertain; there is no automatic retry after crossing the private dispatch boundary. Replays return the fixed saved receipt. Revocation or a changed pinned artifact prevents a new dispatch; already-dispatched Cloudflare effects cannot be recalled.

Capabilities are not accepted from a static configuration flag. The Computer verifies the effective UIDs, the fixed runner binary/version, process visibility protections, private credential channel and a synthetic non-dumpable process-environment canary before reporting ready. It does not print the canary. If any check fails, `secureDeploy:false`, and the API does not decrypt credentials.
